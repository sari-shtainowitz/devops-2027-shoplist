# שיעור 05 - תשובות

## חלק א - מפת ה-cluster


| רכיב | הנהלה / כל node (איפה הוא רץ) | מה הוא עושה, במשפט אחד | אנלוגיה |
|---|---|---|---|
| API server | הנהלה | נקודת הכניסה היחידה ל-cluster, וכל פקודה (גם מ-kubectl) עוברת דרכו | הדלפק של המשרד הראשי, שכל בקשה עוברת דרכו |
| etcd | הנהלה | מסד הנתונים ששומר את כל המצב של ה-cluster, מה קיים ומה צריך להיות | ספר הרישום של הרשת, שבו כתוב הכול |
| scheduler | הנהלה | מחליט על איזה node ירוץ כל pod חדש, לפי המקום הפנוי | הסדרן שמחליט לאיזה סניף לשלוח כל משימה חדשה |
| controller manager | הנהלה | בודק כל הזמן שהמצב בפועל זהה למצב הרצוי, ומתקן כשיש פער | מנהל התפעול שבודק שיש מספיק עובדים בכל סניף וממלא חוסרים |
| kubelet | כל node | סוכן בכל node שמקבל הוראות מההנהלה ודואג שה-pods שלו ירוצו | מנהל הסניף שמבצע את ההוראות מהמשרד הראשי |
| container runtime | כל node | התוכנה שמריצה בפועל את הקונטיינרים (למשל containerd) | העובדים בסניף שעושים את העבודה בפועל |
| kube-proxy | כל node | מנהל את חוקי הרשת כדי שפנייה ל-Service תגיע ל-pod הנכון | המרכזנית שמעבירה כל שיחה לעמדה הנכונה |
| coredns | רץ כ-pods בתוך ה-cluster (namespace kube-system) | DNS פנימי שמתרגם שם של שירות לכתובת, כמו הפנייה לפי שם שירות ב-Docker Compose בשיעור 4 | ספר הטלפונים הפנימי של הרשת |

## חלק ב

### 1. scale
הפקודה kubectl נשלחת ל-API server, שבודק אותה ושומר ב-etcd שהמצב הרצוי הוא 4 עותקים במקום 2.
ה-controller manager רואה פער: רצים 2 וצריך 4. לכן הוא יוצר 2 pods חדשים (עדיין בלי מחשב).
ה-scheduler רואה pods שעוד לא שובצו ומחליט על איזה node כל אחד ירוץ.
ה-kubelet ב-node שנבחר רואה שיש לו pod חדש, ומבקש מה-container runtime להוריד את ה-image ולהפעיל את הקונטיינר.
כשהקונטיינר עולה, ה-kubelet מדווח ל-API server, וה-pod מופיע במצב Running.

### 2. שלוש בלילה
כשהקונטיינר קורס, ה-kubelet ב-node שם לב ומפעיל אותו מחדש בתוך אותו pod. ה-pod נשאר אותו pod, ורק מונה ה-RESTARTS עולה.
אם הקונטיינר ממשיך לקרוס שוב ושוב, ה-kubelet מחכה זמן הולך וגדל בין ניסיון לניסיון (CrashLoopBackOff).
אם מישהי הייתה מוחקת את ה-pod, ה-controller manager היה רואה שחסר עותק ויוצר pod חדש, עם שם חדש וכתובת IP חדשה.
ה-scheduler היה משבץ אותו ב-node, וה-kubelet היה מריץ אותו. ה-Service ממשיך להפנות אליו בלי שום שינוי.

### 3. node נכבה
ה-kubelet ב-node 2 מפסיק לדווח ל-API server, ולכן אחרי זמן קצר ה-controller manager מסמן את ה-node כ-NotReady.
אחרי כמה דקות ה-controller manager מחליט שה-pods שהיו עליו אבודים, ויוצר במקומם pods חדשים.
ה-scheduler משבץ אותם ב-node 1 וב-node 3, שעדיין עובדים, והאפליקציה ממשיכה לרוץ.
ב-Docker Desktop יש node אחד בלבד, וגם ההנהלה רצה עליו. לכן כשהמחשב נכבה, כל ה-cluster נופל ואין לאן להעביר את ה-pods.
כשהמחשב נדלק שוב, ה-cluster עולה מחדש. המצב הרצוי שמור ב-etcd, ולכן ה-pods חוזרים לרוץ.

### 4. מהכיתה לענן
imagePullPolicy: Never אומר "אל תוריד image, תשתמש במה שכבר יש במחשב". בכיתה זה עבד כי בנינו את ה-image על אותו מחשב.
ב-EKS ה-nodes הם מחשבים אחרים בענן, וה-image לא קיים עליהם, ולכן ה-pods לא יעלו.
צריך להעלות את ה-images ל-registry (כמו ECR או Docker Hub), לעדכן ב-YAML את שם ה-image לכתובת ב-registry, ולשנות את imagePullPolicy ל-IfNotPresent או Always.
NodePort פותח פורט על כל node, אבל בענן ה-nodes בדרך כלל לא חשופים לאינטרנט והכתובות שלהם משתנות.
לכן צריך לשנות את סוג ה-Service ל-LoadBalancer, שיוצר כתובת חיצונית קבועה.

### 5. pod בודד
pod שנוצר עם kubectl run הוא pod "יתום": אין אף רכיב שאחראי לשמור שהוא קיים.
ה-pod של web שייך ל-Deployment, וה-controller manager דואג כל הזמן שיהיה מספר העותקים שהוגדר. לכן כשמוחקים pod, הוא יוצר חדש.
כשמוחקים את ה-pod של stats, אין מי שישים לב שהוא חסר, ולכן הוא לא חוזר.
כדי ש-stats יחזור תמיד, צריך להריץ אותו דרך Deployment (קובץ YAML עם kind: Deployment) ולא כ-pod בודד.
